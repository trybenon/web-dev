# Совместный просмотр видео

Учебный проект для синхронного просмотра видео в браузере.

## Структура

- client/ — клиент на Vue 3, TypeScript и Vite.
- server/ — HTTP-сервер на Node.js и TypeScript.
- shared/ — общий пакет типов и кода.
- docs/ — документация проекта.

Клиент и сервер подключают @watch-together/shared
как локальную зависимость через file:../shared.

## Подготовка

Нужны Node.js и npm.
Каркас проверен на Node.js 25.2.1 и npm 11.6.2.

Установка зависимостей из корня репозитория:

```bash
npm ci
```

## Разработка

```bash
npm run dev
```

Команда сначала собирает shared, затем запускает клиент и сервер.

- Клиент: http://localhost:5173/
- API через Vite: http://localhost:5173/api/health
- Сервер напрямую: http://127.0.0.1:3000/api/health

API проверки состояния возвращает {"status":"ok"}.

После изменения shared нужно перезапустить npm run dev,
чтобы пересобрать общий пакет.

## Сборка

```bash
npm run build
```

Пакеты собираются в порядке: shared, server, client.
Команда включает проверку типов TypeScript.

## Запуск собранного сервера

После сборки:

```bash
npm run start --workspace=server
```

Проксирование /api в конфиге Vite настроено для разработки.
Публикация приложения пока не настроена.

## Мониторинг ошибок в Bugsink

Создайте проект в Bugsink и скопируйте его DSN со страницы подключения. Для локального запуска замените `<DSN_ПРОЕКТА>` своим значением в двух местах.

1. Для Vue добавьте строку в локальный файл `client/.env.local`. Git игнорирует этот файл.

   ```dotenv
   VITE_BUGSINK_DSN=<DSN_ПРОЕКТА>
   ```

2. Для Node передайте DSN при запуске из корня репозитория.

   ```bash
   BUGSINK_DSN='<DSN_ПРОЕКТА>' npm run dev
   ```

Клиент и сервер включают мониторинг независимо, когда задан их DSN. Для привязки ошибок к версии передайте один SHA коммита в `VITE_APP_RELEASE` при сборке клиента и в `APP_RELEASE` при запуске сервера. Для опубликованного сервера задайте `NODE_ENV=production`.

### Загрузка source maps для Vue

Соберите приложение командой `npm run build`. Затем выполните команду ниже отдельно и введите API-токен Bugsink с правом загрузки карт в выбранный проект.

```bash
read -rs BUGSINK_AUTH_TOKEN
```

Запустите скрипт из корня репозитория. В `BUGSINK_URL` укажите адрес панели Bugsink, а в `BUGSINK_PROJECT` — slug проекта.

```bash
BUGSINK_URL='<АДРЕС_ПАНЕЛИ_BUGSINK>' \
BUGSINK_PROJECT='<SLUG_ПРОЕКТА>' \
```

Скрипт добавляет одинаковые debug ID в JavaScript и карты из `client/dist` и загружает их в Bugsink. Для локальной проверки запустите `npm run preview -w client` на этой сборке. При деплое публикуйте JavaScript из той же сборки после загрузки карт.

## Unit-тесты

Однократный запуск:

```bash
npm run test
```

Запуск с повторной проверкой при изменении файлов:

```bash
npm run test:watch
```

Используется Vitest. Тесты находятся в client/src, server/src
и shared/src в файлах с окончанием .test.ts.

Пример: client/src/api.test.ts проверяет успешный ответ,

## E2E-тесты

Перед первым запуском установите Chromium для Playwright:

```bash
npx playwright install chromium
```

Запуск тестов:

```bash
npm run e2e
```

Playwright автоматически запускает сервер на http://127.0.0.1:3000 и клиент на http://127.0.0.1:4173.
Порты 3000 и 4173 должны быть свободны, отдельно запускать приложение не нужно.

Сценарии:

- главная страница отвечает 200 и показывает заголовок «Совместный просмотр видео»;
- две вкладки страницы проверки синхронизации входят в одну комнату, стартуют вместе (расхождение меньше 150 мс), а пауза и перемотка из любой вкладки доходят до другой. Сценарию нужен деморолик `client/public/media/demo.webm`; без него он пропускается.

Запуск с видимым окном браузера:

```bash
npm run e2e:headed
```

Просмотр HTML-отчёта последнего запуска:

```bash
npm run e2e:report
```

При ошибке сохраняются снимок страницы и trace в test-results/.
Отчёты и результаты запусков не включаются в Git.

## Покрытие тестами

Запуск тестов с отчётом о покрытии:

```bash
npm run coverage
```

Краткий отчёт выводится в терминал, HTML-отчёт создаётся в coverage/index.html.

Минимальный общий порог - 80% по каждой метрике: строки, функции, ветвления и инструкции.
При недостаточном покрытии команда завершается с ошибкой.

В отчёт включены исходники client/src, server/src и shared/src, в том числе файлы, которые ещё не импортируются тестами.

Исключены:

- тестовые файлы и файлы описаний типов .d.ts;
- client/src/main.ts — подключение Vue, Pinia и Element Plus к странице;
- server/src/index.ts — запуск сервера на фиксированном порту;
- shared/src/index.ts — сейчас содержит только интерфейс TypeScript.
  При добавлении исполняемой логики в исключённые файлы
  необходимо пересмотреть исключения.

Проверки серверных HTTP-ответов сами запускают локальный сервер
на свободном порту и закрывают его после завершения.

## Запуск через Docker Compose

Нужен запущенный Docker Desktop с Docker Compose v2. Для `make run` также
нужен `make` (на macOS доступен в Command Line Tools). Node.js и npm на хосте
не требуются. Если `make` не установлен, используйте эквивалентную команду
`docker compose up --build`.

Из корня репозитория:

```bash
make run
```

После сборки и запуска приложение открывается на http://localhost:3000,
проверка сервера — http://localhost:3000/api/health.
Первый запуск скачивает базовый образ и npm-зависимости; нужен интернет.
Следующие сборки используют кеш Docker. Остановить запуск — Control + C.

Полезные команды:

```bash
make status  # состояние контейнера, включая healthcheck
make logs    # журнал приложения
make stop    # остановить и удалить контейнеры
```

Если порт 3000 занят локальным `npm run dev`, остановите его или выберите
другой порт. Например:

```bash
APP_PORT=4000 make run
```

Для постоянной настройки можно скопировать `.env.example` в `.env` и изменить
`APP_PORT`. Без `.env` работают значения по умолчанию. `APP_BIND=127.0.0.1`
публикует порт только локально; `APP_BIND=0.0.0.0` разрешает подключения с
других устройств. Внутри контейнера сервер слушает `0.0.0.0:3000`.

Dockerfile собирает `shared`, затем `server` и `client`. В итоговый образ
попадают собранные файлы и production-зависимости сервера и shared;
Vite и TypeScript при запуске не используются. Один Node-процесс отдаёт
клиент и API, а также обслуживает WebSocket `/ws`.
Ключи LiveKit не требуются для запуска.

Сборка выбирает архитектуру компьютера автоматически: на Apple Silicon —
arm64, на Intel/AMD — amd64. Workflow `Docker` собирает и проверяет запуск
обоих вариантов; arm64 на GitHub Runner проверяется через QEMU.
Образы пока не публикуются и не деплоятся: это отдельная задача #43.

Проверка готовности запрашивает `/api/health` внутри контейнера. Для запуска
в фоне с ожиданием готовности:

```bash
docker compose up --build --detach --wait
```

Деморолик из #24 попадёт в контейнер вместе с клиентом после включения файла
в текущую ветку. Секреты `.env`, локальные зависимости и результаты предыдущих
сборок исключены из Docker build context.

## HTTP-сервер приложения

Сборка всех пакетов и запуск собранного сервера:

```bash
npm run build
npm run start --workspace=server
```

По умолчанию сервер доступен на http://127.0.0.1:3000.

Адрес и порт задаются переменными окружения:

```bash
HOST=0.0.0.0 PORT=4000 npm run start --workspace=server
```

HOST=0.0.0.0 позволяет принимать подключения через доступные сетевые интерфейсы, в том числе при запуске в контейнере. PORT должен быть целым числом от 1 до 65535.

Сервер предоставляет:

- GET /api/health - ответ {"status":"ok"};
- GET / - HTML собранного клиента из client/dist;
- GET /assets/... - JavaScript, CSS и другие файлы сборки;
- GET /favicon.svg и GET /icons.svg - файлы иконок;
- GET /media/demo.webm - выдачу демофайла целиком или по диапазону байтов.

Демонстрационный ролик нужно положить в client/public/media/demo.webm.

При сборке клиента Vite копирует его в client/dist/media/demo.webm. Собранный HTTP-сервер отдаёт видео по адресу /media/demo.webm. В режиме разработки этот же адрес обслуживает Vite.

Не храните исходный ролик только в client/dist: эта папка пересоздаётся при сборке. Добавление ролика относится к задаче #24.
Поддерживаются одиночные диапазоны Range: bytes=начало-конец, bytes=начало- и bytes=-количество. Успешный частичный ответ имеет статус 206. Некорректный, неподдерживаемый или невыполнимый диапазон получает 416.

Для GET-запросов, принимающих text/html, пути без расширения получают index.html как fallback. Адреса /api, /assets и /media вместе с их вложенными путями исключены из fallback. Неизвестные API и отсутствующие файлы возвращают 404.

HTTP-тесты создают временные файлы и запускают сервер на свободном порту. Они не требуют предварительной сборки клиента или настоящего видеоролика.

## Демонстрационный ролик

В комнате используется `client/public/media/demo.webm` длительностью около
90 секунд. Это [Grand Theft Auto VI Launch Trailer](https://www.rockstargames.com/VI/launch-trailer)
от Rockstar Games. Сведения об исходной копии, перекодировании и правах
записаны в `client/public/media/demo.LICENSE.txt`. Название и ссылка на
официальную публикацию видны рядом с видео в комнате.

Файл в формате WebM содержит видео VP9 (640 × 360, 30 кадров/с, yuv420p) и
стереозвук Opus (48 кГц). Демо доступно по `/media/demo.webm` с того же origin,
что и приложение. В разработке файл отдаёт Vite, а после `npm run build` —
HTTP-сервер.

Проверка: `npm run e2e -- e2e/demo.spec.ts` проверяет выдачу и фактическое
воспроизведение файла в Chromium. Перед закрытием #24 также нужно вручную
проверить звук и воспроизведение в Chrome, Firefox и Safari, включая переход
к другой позиции ролика. Playwright-тест не заменяет проверку Safari.

## WebSocket-шлюз

Шлюз подключён к тому же HTTP-серверу по пути /ws.
При стандартных настройках адрес: ws://127.0.0.1:3000/ws.

Входящие сообщения проверяются функцией parseClientMessage из shared. Неверный JSON, неизвестный тип, некорректные поля и бинарные сообщения получают error с кодом invalid_message. Соединение остаётся открытым.

### Ограничения и проверка соединения

- Максимальный размер сообщения - 64 КиБ. При превышении соединение закрывается с кодом 1009.
- По умолчанию разрешено 30 сообщений за фиксированное окно в 1 секунду на каждое подключение. Учитываются также некорректные сообщения.
- Сообщения сверх лимита отбрасываются. Ошибка rate_limited отправляется не чаще одного раза в секунду, соединение сохраняется.
- Служебный WebSocket ping отправляется каждые 15 секунд. Если к следующей проверке pong не получен, соединение завершается.
- Сообщение протокола sync:ping обрабатывается отдельно: сервер отвечает sync:pong с временными отметками t0, t1 и t2.

### Передача сообщений обработчикам

attachWebSocketGateway принимает необязательные обработчики:

- onMessage(client, message) — получает проверенные сообщения, кроме sync:ping, на который шлюз отвечает самостоятельно
- onClose(client) — вызывается при закрытии соединения, до очистки принадлежности к комнате.

Оба обработчика могут возвращать void или Promise<void>. Синхронные исключения и отказы Promise перехватываются и записываются в журнал. Ошибка onMessage закрывает затронутое открытое соединение с кодом 1011. Ошибка onClose не мешает очистке подключения.

Если асинхронному onClose нужен roomId после await, обработчик должен сохранить его в локальную переменную до первого await. Шлюз не ожидает завершения обработчика перед очисткой подключения.

Объект client предоставляет:

- connectionId — идентификатор текущего подключения
- roomId — текущую комнату типа RoomId из shared или null
- send(message) — отправку сообщения этому подключению
- close(code?, reason?) — закрытие соединения; по умолчанию код 1000
- joinRoom(roomId) — назначение комнаты серверным кодом
- leaveRoom() - удаление принадлежности к комнате
- broadcast(message) - рассылку всем подключениям текущей комнаты, включая отправителя.

Возвращаемый объект шлюза предоставляет broadcastToRoom(roomId, message). Этот метод позволяет рассылать события из серверных обработчиков и таймеров без подключения-отправителя.

При закрытии соединения его принадлежность к комнате очищается, а подключение удаляется из списка рассылки.

### Серверное время

Функция serverNow() из server/src/clock.ts возвращает монотонное время в миллисекундах на основе performance.now(). Шлюз использует её для t1 и t2, ограничитель частоты — по умолчанию для расчёта окон.

Серверные anchorServerTime, hold.deadline и другие временные отметки синхронизации должны использовать те же часы. Значения не являются временем Unix и не сохраняют смысл после перезапуска процесса.

### Подключение в режиме разработки

Vite проксирует /api и WebSocket-подключения /ws на сервер 127.0.0.1:3000. При стандартном запуске через npm run dev браузер может подключаться к ws://localhost:5173/ws.

### Поведение до входа в комнату

До входа разрешены room:create, room:join и sync:ping.
Сообщение room:leave вне комнаты молча игнорируется.
Для остальных корректных сообщений возвращается not_joined.

Повторные room:create и room:join внутри комнаты игнорируются.

### Комнаты и присутствие

В server/src/index.ts подключён RoomService: он обрабатывает сообщения комнат через WebSocket-шлюз.

- room:create создаёт комнату и сразу добавляет создателя
- room:join добавляет участника в существующую комнату. Неизвестная комната возвращает room_not_found, попытка добавить пятого участника - room_full
- Сервер выдаёт каждому участнику peerId и sessionToken. Токены других участников не передаются клиенту
- При обрыве соединения участник получает статус reconnecting, а его место сохраняется на 30 секунд
- Возвращение с действующим sessionToken в ту же комнату сохраняет peerId. Если прежнее соединение ещё открыто, сервер закрывает его с кодом 4001
- После истечения 30 секунд участник удаляется. Вход с истёкшим или неизвестным токеном в существующую комнату считается новым входом
- room:leave удаляет участника сразу. Комната удаляется, когда в ней больше нет участников, включая ожидающих переподключения
- presence:update передаёт серверу состояние плеера участника. Сервер рассылает presence:sync со списком состояний и статусами соединений раз в секунду

Комнаты и сессии хранятся в памяти процесса и исчезают при перезапуске сервера.

RoomService передаёт сообщения управления воспроизведением и источником в Room. Проверка таймеров состояния воспроизведения запускается каждые 100 мс.

### Проверка комнат

Из корня проекта выполните:

    npm run test -- server/src/room.test.ts server/src/room-service.test.ts server/src/room-delivery.test.ts server/src/room-websocket.test.ts

Проверяются создание комнаты, вход и выход, вместимость, восстановление сессии, замена соединения, удаление пустых комнат и доставка сообщений. Интеграционные тесты используют настоящие WebSocket-подключения.

### Проверка шлюза

Из корня проекта выполните:

    npm run test -- server/src/rate-limit.test.ts server/src/ws-gateway.test.ts

Тесты используют настоящие WebSocket-подключения к локальному серверу. Проверяются общие примеры протокола из shared, обработка ошибок, ограничения, heartbeat, передача сообщений обработчику, рассылка внутри комнаты и очистка принадлежности при отключении.

## Синхронизация на клиенте

Код — в `client/src/sync`. Интерфейс берёт всё из `client/src/sync/index.ts`:
`createSyncClient()` подключается к серверу, `createPlayerBridge(client, video)`
связывает комнату с элементом `<video>`. Заглушки `createStubSyncClient`
и `createStubPlayerBridge` остаются для тестов интерфейса без сервера.

- `clock.ts`, `server-clock.ts` — смещение часов по `sync:ping` / `sync:pong`;
- `timeline.ts` — позиция комнаты, момент старта, перевод между часами воркера, страницы и сервера;
- `engine.ts` — соединение, вход и возвращение по токену, состояние комнаты, отчёты о готовности, команды плееру;
- `sync.worker.ts` — воркер, в котором работает `engine.ts`;
- `client.ts` — `SyncClient` на странице поверх воркера;
- `player-bridge.ts` — выполняет команды воркера на `<video>` и докладывает о плеере.

Контура подстройки скорости пока нет: если плеер ушёл от комнаты больше чем
на секунду, воркер просто перематывает его.
