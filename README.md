# Совместный просмотр видео

Учебный проект для синхронного просмотра видео в браузере.

## Структура

- client/ — клиент на Vue 3, TypeScript и Vite.
- server/ — HTTP-сервер на Node.js и TypeScript.
- shared/ — общий пакет типов и кода.
- docs/ — документация проекта.

Клиент и сервер подключают @watch-together/shared
как локальную зависимость через file:../shared.

## Подготовка

Нужны Node.js и npm.
Каркас проверен на Node.js 25.2.1 и npm 11.6.2.

Установка зависимостей из корня репозитория:

```bash
npm ci
```

## Разработка

```bash
npm run dev
```

Команда сначала собирает shared, затем запускает клиент и сервер.

- Клиент: http://localhost:5173/
- API через Vite: http://localhost:5173/api/health
- Сервер напрямую: http://127.0.0.1:3000/api/health

API проверки состояния возвращает {"status":"ok"}.

После изменения shared нужно перезапустить npm run dev,
чтобы пересобрать общий пакет.

## Сборка

```bash
npm run build
```

Пакеты собираются в порядке: shared, server, client.
Команда включает проверку типов TypeScript.

## Запуск собранного сервера

После сборки:

```bash
npm run start --workspace=server
```

Проксирование /api в конфиге Vite настроено для разработки.
Публикация приложения пока не настроена.

## Проверка кода и форматирование

Все команды выполняются из корня репозитория.

Проверка JavaScript, TypeScript и CSS:

```bash
npm run lint
```

Автоматическое форматирование:

```bash
npm run format
```

Проверка форматирования без изменения файлов:

```bash
npm run format:check
```

• ESLint использует общий корневой конфиг для client, server и shared.
• Stylelint проверяет CSS клиента.
• Prettier задаёт единое оформление кода и конфигураций.
• Документация в docs/ и отдельные спайки исключены из этих проверок.

## Unit-тесты

Однократный запуск:

```bash
npm run test
```

Запуск с повторной проверкой при изменении файлов:

```bash
npm run test:watch
```

Используется Vitest. Тесты находятся в client/src, server/src
и shared/src в файлах с окончанием .test.ts.

Пример: client/src/api.test.ts проверяет успешный ответ,
HTTP-ошибку и сетевую ошибку функции getHealth.
HTTP-запросы подменяются в тестах, запуск сервера не требуется.

## E2E-тесты

Перед первым запуском установите Chromium для Playwright:

```bash
npx playwright install chromium
```

Запуск тестов:

```bash
npm run e2e
```

Playwright автоматически запускает клиент на http://127.0.0.1:4173.
Порт 4173 должен быть свободен, отдельно запускать приложение не нужно.

Сценарий открывает главную страницу, проверяет HTTP-статус 200 и видимость заголовка «Совместный просмотр видео».

Запуск с видимым окном браузера:

```bash
npm run e2e:headed
```

Просмотр HTML-отчёта последнего запуска:

```bash
npm run e2e:report
```

При ошибке сохраняются снимок страницы и trace в test-results/.
Отчёты и результаты запусков не включаются в Git.

## Покрытие тестами

Запуск тестов с отчётом о покрытии:

```bash
npm run coverage
```

Краткий отчёт выводится в терминал, HTML-отчёт создаётся в coverage/index.html.

Минимальный общий порог - 80% по каждой метрике: строки, функции, ветвления и инструкции.
При недостаточном покрытии команда завершается с ошибкой.

В отчёт включены исходники client/src, server/src и shared/src, в том числе файлы, которые ещё не импортируются тестами.

Исключены:

- тестовые файлы и файлы описаний типов .d.ts;
- client/src/main.ts — подключение Vue, Pinia и Element Plus к странице;
- server/src/index.ts — запуск сервера на фиксированном порту;
- shared/src/index.ts — сейчас содержит только интерфейс TypeScript.
  При добавлении исполняемой логики в исключённые файлы
  необходимо пересмотреть исключения.

Проверки серверных HTTP-ответов сами запускают локальный сервер
на свободном порту и закрывают его после завершения.

## CI

Workflow .github/workflows/ci.yml запускает проверки при создании и обновлении pull request, а также при отправке изменений в main.

Среда выполнения: Ubuntu, Node.js 24.

Отдельно выполняются:

- проверка форматирования;
- ESLint и Stylelint;
- unit-тесты;
- тесты с проверкой порога покрытия 80%;
- сборка;
- e2e-тест в Chromium.

Результаты доступны во вкладке Checks соответствующего PR и во вкладке Actions репозитория. Отчёты Playwright сохраняются как артефакт playwright-results на 7 дней.

Обязательность успешных проверок для слияния настраивается отдельно в правилах защиты main.

## HTTP-сервер приложения

Сборка всех пакетов и запуск собранного сервера:

```bash
npm run build
npm run start --workspace=server
```

По умолчанию сервер доступен на http://127.0.0.1:3000.

Адрес и порт задаются переменными окружения:

```bash
HOST=0.0.0.0 PORT=4000 npm run start --workspace=server
```

HOST=0.0.0.0 позволяет принимать подключения через доступные сетевые интерфейсы, в том числе при запуске в контейнере. PORT должен быть целым числом от 1 до 65535.

Сервер предоставляет:

- GET /api/health - ответ {"status":"ok"};
- GET / - HTML собранного клиента из client/dist;
- GET /assets/... - JavaScript, CSS и другие файлы сборки;
- GET /favicon.svg и GET /icons.svg - файлы иконок;
- GET /media/demo.webm - выдачу демофайла целиком или по диапазону байтов.

Для демо ожидается файл client/dist/media/demo.webm. Сам ролик и сведения о его лицензии добавляются отдельно в задаче #24. Пока файла нет, запрос видео возвращает 404.

Поддерживаются одиночные диапазоны Range: bytes=начало-конец, bytes=начало- и bytes=-количество. Успешный частичный ответ имеет статус 206. Некорректный, неподдерживаемый или невыполнимый диапазон получает 416.

Для GET-запросов, принимающих text/html, пути без расширения получают index.html как fallback. Адреса /api, /assets и /media вместе с их вложенными путями исключены из fallback. Неизвестные API и отсутствующие файлы возвращают 404.

HTTP-тесты создают временные файлы и запускают сервер на свободном порту. Они не требуют предварительной сборки клиента или настоящего видеоролика.

## WebSocket-шлюз

Шлюз подключён к тому же HTTP-серверу по пути /ws.
При стандартных настройках адрес: ws://127.0.0.1:3000/ws.

Входящие сообщения проверяются функцией parseClientMessage из shared. Неверный JSON, неизвестный тип, некорректные поля и бинарные сообщения получают error с кодом invalid_message. Соединение остаётся открытым.

### Ограничения и проверка соединения

- Максимальный размер сообщения - 64 КиБ. При превышении соединение закрывается с кодом 1009.
- По умолчанию разрешено 30 сообщений за фиксированное окно в 1 секунду на каждое подключение. Учитываются также некорректные сообщения.
- Сообщения сверх лимита отбрасываются. Ошибка rate_limited отправляется не чаще одного раза в секунду, соединение сохраняется.
- Служебный WebSocket ping отправляется каждые 15 секунд. Если к следующей проверке pong не получен, соединение завершается.
- Сообщение протокола sync:ping обрабатывается отдельно: сервер отвечает sync:pong с временными отметками t0, t1 и t2.

### Передача сообщений обработчику

attachWebSocketGateway принимает необязательный синхронный обработчик onMessage(client, message). Он получает проверенные сообщения, кроме sync:ping, на который шлюз отвечает самостоятельно.

Объект client предоставляет:

- connectionId - идентификатор текущего подключения
- roomId - текущая комната или null
- send(message) - отправку сообщения этому подключению
- joinRoom(roomId) - назначение комнаты серверным кодом
- leaveRoom() - удаление принадлежности к комнате
- broadcast(message) - рассылку всем подключениям текущей комнаты,
  включая отправителя

При закрытии соединения его принадлежность к комнате очищается, а подключение удаляется из списка рассылки.

### Поведение до входа в комнату

До входа разрешены room:create, room:join и sync:ping.
Сообщение room:leave вне комнаты молча игнорируется.
Для остальных корректных сообщений возвращается not_joined.

Повторные room:create и room:join внутри комнаты игнорируются.

### Границы реализации

Шлюз предоставляет транспорт и рассылку. Создание комнат, проверка их существования и вместимости, восстановление участника через sessionToken и обработка состояния комнаты относятся к задаче #19.

В текущем запуске сервера обработчик onMessage ещё не подключён: сообщения room:create и room:join сами по себе комнаты не создают.

### Проверка шлюза

Из корня проекта выполните:

    npm run test -- server/src/rate-limit.test.ts server/src/ws-gateway.test.ts

Тесты используют настоящие WebSocket-подключения к локальному серверу. Проверяются общие примеры протокола из shared, обработка ошибок, ограничения, heartbeat, передача сообщений обработчику, рассылка внутри комнаты и очистка принадлежности при отключении.
