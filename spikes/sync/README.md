# Спайк: синхронизация воспроизведения

Прототип ядра синхронизации для задач #3 и #4 (и скелеты #5, #11).
Отвечает на вопрос «работает ли архитектура из `docs/` на самом деле»
и даёт измеренные числа вместо догадок.

Это **не продукт**: здесь нет React, стейт-менеджера, библиотеки компонентов,
голосового чата и отпечатка файла. В проект переносится чистое ядро
(`core/`, `shared/`) вместе с тестами — оно не зависит от окружения.

## Быстрый старт

Нужны Node 22.18+ (лучше 24 LTS) и ffmpeg с libvpx-vp9 и libopus.

```bash
npm install
npm run video      # сгенерировать тестовое видео (90 с, WebM VP9 + Opus)
npm start          # сервер на http://localhost:8787
```

Откройте `http://localhost:8787/?room=demo` в **двух окнах рядом** (не во вкладках
одного окна — скрытая вкладка ведёт себя иначе, см. ниже), введите имена,
нажмите «Присоединиться» в обоих и «Играть» в одном.

На кадре крупный таймкод и номер кадра, а в начале каждой секунды — короткий
«бип». Если окна рассинхронизированы, бип слышен эхом. Это самая быстрая
ручная проверка.

Справа — состояние синхронизации: смещение часов, мост между воркером и окном,
ошибка, текущая скорость, режим контура, число перемоток.

Полезные параметры адреса:

| Параметр | Что делает |
|---|---|
| `room=имя` | комната |
| `lag=lagUp%3D60%26lagDown%3D60` | сервер задерживает сообщения этого клиента (60 мс туда, 60 обратно) |
| `seekOnly=1` | режим «только перемотка», как в Safari |
| `mute=volume0` / `mute=muted` | выключить звук фильма громкостью или через `muted` (для опытов с фоном) |
| `frames=0` | не использовать rVFC, только опрос `currentTime` |
| `src=/путь` | другой ролик |

В консоли любого окна: `__sync.video.currentTime += 0.3` — искусственный сбой
на 300 мс, чтобы посмотреть, как контур его гасит.

## Тесты

```bash
npm test           # 77 тестов ядра
npm run coverage   # покрытие: 100 % строк, 98 % ветвлений
npm run typecheck
```

Покрытие считается по `core/` и `shared/`. Воркер, `client/main.ts` и сервер —
тонкие адаптеры; их проверяют сценарии замера.

## Автоматический замер

```bash
npm run measure                 # все сценарии, по одному разу
REPEAT=3 npm run measure        # по три раза, в конце таблица медиан
npm run measure -- kick         # один сценарий
```

Нужен Chromium: `npx playwright install chromium` или путь к любому Chrome
в `CHROMIUM_PATH`. Каждый участник — отдельный контекст браузера. Расхождение
считается по абсолютному времени (у вкладок одной машины одни часы), а не по
самооценке клиентов. Результаты — в `results/`.

| Сценарий | Что проверяет |
|---|---|
| `start` | старт, пауза и повторный старт двух участников |
| `lag` | у одного RTT 120 мс |
| `asym` | асимметрия 100/0 мс — известное ограничение NTP |
| `kick` | сбой на 300 мс (скоростью) и на 900 мс (перемоткой) |
| `latejoin` | вход посреди просмотра |

### Результаты (headless Chromium 141, Linux, 2 ядра)

Два независимых прогона по три повтора; медианы каждого прогона и диапазон
по всем шести повторам.

| Сценарий | Что мерили | Прогон 1 | Прогон 2 | Все 6 |
|---|---|---|---|---|
| Старт | расхождение в момент старта | 4 мс | 2 мс | −17…+8 мс |
| | держится, 95-й перцентиль | 6 мс | 18 мс | 4–35 мс |
| Повторный старт | в момент старта | 15 мс | 61 мс | 0–83 мс |
| RTT 120 мс | держится, 95-й перцентиль | 8 мс | 2 мс | 0–19 мс |
| Асимметрия 100/0 | реальное расхождение | 42 мс | 57 мс | 36–64 мс; самооценка клиента 17–24 мс |
| Сбой 300 мс | до расхождения < 30 мс | 9.7 с | 8.7 с | 8.3–10.7 с, без перемоток |
| Сбой 900 мс | до расхождения < 30 мс | 3.7 с | 5.4 с | 2.3–6.2 с, одна перемотка |
| Вход посреди просмотра | от клика до игры | 0.98 с | 0.96 с | комната не останавливалась |
| | держится, 95-й перцентиль | 22 мс | 22 мс | 19–42 мс |
| Точки отсчёта воркера и окна | разница | 61 мс | 49 мс | 45–76 мс; в опытах с фоном до 95 |

Разброс между прогонами большой, хотя логика синхронизации не менялась:
машина перегружена (две вкладки декодируют VP9 на двух ядрах), и в headless
нет звуковой карты. Это порядок величины; на ноутбуках нужно перемерить.

## Фоновая вкладка (задача #4)

### Вручную, в любом браузере

Откройте `http://localhost:8787/background/`, выберите режим звука, нажмите
«Старт», уйдите на другую вкладку на 30 с (или на 6 минут — проверка жёсткого
дросселирования Chrome), вернитесь. Таблица покажет, что происходило, пока
вкладка была скрыта. «Скопировать отчёт» — JSON для чата команды.

### Автоматически, в настоящем Chrome

Headless-режим не умеет честно скрывать вкладку, поэтому опыты запускают
обычный Chrome (на Linux без экрана — под `xvfb-run`) и скрывают вкладку
второй вкладкой в том же окне.

```bash
npm start   # в отдельном терминале
EXE=/путь/к/chrome MODE=muted HIDE=15000 xvfb-run -a node tools/background-probe.mjs
EXE=/путь/к/chrome MUTE=volume0 HIDE=20000 xvfb-run -a -s "-screen 0 1600x900x24" node tools/hidden-tab.mjs
```

На ноутбуке `xvfb-run` не нужен — откроются настоящие окна.

### Что показали опыты (Chromium 141)

| Что | Результат |
|---|---|
| Таймер воркера в скрытой вкладке | 158–159 срабатываний из 159 — не дросселируется |
| Таймер окна, вкладка со звуком | 159 из 159 — звучащая вкладка не дросселируется |
| Таймер окна, без звука | 15–16 из 159 — раз в секунду |
| Сообщения воркер → скрытое окно | 0–1 мс задержки даже при задушенных таймерах окна |
| rVFC в скрытой вкладке | 0 вызовов |
| Видео с `muted` с самого начала | браузер ставит на паузу, потеряны все 16 с |
| Видео с `volume = 0` | играет, 0 мс ухода |
| Видео в скрытой вкладке до первой загрузки | не грузится вообще (`readyState` 0) |
| Синхронизация участника, скрытого на 20 с | со звуком — всплеск до ~100 мс, погашен за ~10 с; `volume = 0` — 1–2 мс |

## Устройство

```
shared/protocol.ts     сообщения клиент ↔ сервер и их проверка
core/clock.ts          оценка смещения часов (NTP, 4 метки, лучшая по задержке)
core/controller.ts     контур дрейфа: фильтр, гистерезис, скорость, перемотка, обучение
core/timeline.ts       перевод шкал времени, целевая позиция, план старта
core/room.ts           состояние комнаты на сервере: ревизии, барьер, якорь
server/main.ts         HTTP + WebSocket, снятие типов для браузера, пульс, задержки для опытов
client/main.ts         главный поток: video, rVFC, исполнение команд
client/sync.worker.ts  воркер: сокет, часы, мост к окну, контур, опрос в фоне
background/            страница проверки фоновой вкладки
tools/                 генерация видео, замеры, опыты со скрытием
tests/                 unit-тесты ядра
```

Решения и пороги с обоснованием — в `docs/sync-drift.md`.

## Как перенести в проект

1. `shared/protocol.ts` → пакет `shared/`, проверку сообщений переписать на zod.
2. `core/clock.ts`, `core/controller.ts`, `core/timeline.ts` → клиент, рядом с воркером.
3. `core/room.ts` → сервер; адаптер `server/main.ts` взять за образец.
4. Тесты переносятся как есть (Vitest).
5. `client/main.ts` не переносить: в проекте это React-компонент плеера
   и стейт-менеджер. Но правило оттуда обязательно: события `video` никогда
   не превращаются в намерения комнаты.
