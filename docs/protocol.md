# Протокол

Описание обмена между клиентом и сервером на уровне проектирования: какие
сообщения есть, что они несут и почему устроены именно так. Точные структуры
данных появятся при реализации.

Сценарии использования — в `sync-start.md`, `sync-latejoin.md`, `sync-drift.md`.
Общее устройство — в `architecture.md`. Работающая реализация протокола —
в прототипе: ветка `spike/sync`, файл `spikes/sync/shared/protocol.ts`.
Голос и текстовый чат идут через LiveKit, а не через этот протокол:
здесь только выдача пропуска туда. Подробно — документ A `voise-text-chats.md`.

---

## Соглашения

**Транспорт.** WebSocket между клиентом и сервером. Соединение держит воркер
синхронизации, а не главный поток.

**Время.** Единственная общая шкала — серверная. Клиент не доверяет системным
часам, потому что они могут скачком измениться, и для собственных измерений
использует монотонный счётчик.

**Источник правды.** Состояние воспроизведения принадлежит серверу. Клиент
присылает намерение, сервер решает и рассылает результат всем. Своё состояние
клиент не меняет до подтверждения — иначе при отклонении пришлось бы
откатываться, и пользователь увидел бы рывок.

**Управление общее.** Перемотка, пауза и запуск, сделанные любым участником,
применяются ко всей комнате. Отдельной роли хоста нет.

**Видеоданные по этому каналу не ходят никогда.** Ни файл, ни буфер.

## Сообщения клиент ↔ сервер

### Комната

| Сообщение | Направление | Зачем |
|---|---|---|
| `room:join` | клиент → сервер | вход в комнату; после обрыва — с токеном сессии (предложено) |
| `room:state` | сервер → клиенту | полный снапшот: кто внутри, что играет, в какой позиции, какой источник; мой `peerId` и токен сессии (предложено) |
| `room:peer_joined` / `room:peer_left` | сервер → всем | кто-то вошёл или вышел |

Снапшот бесполезен, пока клиент не откалибровал часы: позиция в нём привязана
к серверному времени, которое новичок ещё не умеет переводить в своё.

**Возвращение после обрыва** (`decisions.md`, 2.12; предложено, ждёт
подтверждения A и C). При входе сервер выдаёт участнику `peerId` и случайный
токен сессии. Токен живёт только в памяти воркера синхронизации — того,
кто держит соединение. Соединение оборвалось — сервер 30 секунд держит
место: участник остаётся в списке со статусом «переподключается», барьер
его не ждёт, `room:peer_left` не рассылается. Воркер переподключается,
присылает `room:join` с токеном и получает тот же `peerId` и свежий
снапшот. Если сервер ещё считал старое соединение живым, он его закрывает:
у одного `peerId` одно соединение. Через 30 секунд без возвращения сервер
удаляет участника и рассылает `room:peer_left`.

Перезагрузка страницы и новая вкладка — это новый вход с новым `peerId`:
токена в памяти уже нет. Так требует документ A (`voise-text-chats.md`,
раздел 3.2): в LiveKit `peerId` служит именем участника, и двух подключений
с одним именем быть не должно.

### Часы

| Сообщение | Направление | Зачем |
|---|---|---|
| `sync:ping` | клиент → сервер | метка времени отправителя `t0` |
| `sync:pong` | сервер → клиенту | `t0` без изменений, момент приёма `t1` и момент отправки `t2` по часам сервера |

Клиент добавляет четвёртую метку `t3` — момент получения ответа — и считает
по схеме NTP: задержка `(t3 − t0) − (t2 − t1)`, смещение
`((t1 − t0) + (t2 − t3)) / 2`. Из последних восьми замеров берётся тот,
у которого задержка меньше всего: у него меньше всего очередей, значит,
оценка точнее. Серия из восьми частых пингов — на старте, после
переподключения и после возврата вкладки из фона; дальше раз в 5 секунд.
Пинги заодно служат пульсом соединения.

Ограничение: если задержки туда и обратно заметно различаются, оценка
ошибается на половину разницы, и клиент этого не видит. В прототипе
асимметрия 100/0 мс дала скрытое смещение 42–57 мс.

### Источник видео

| Сообщение | Направление | Зачем |
|---|---|---|
| `source:propose` | клиент → сервер | кто-то выбрал файл: отпечаток, длительность, имя |
| `source:state` | сервер → всем | какой источник у комнаты и у кого он сошёлся |
| `source:matched` | клиент → сервер | мой файл совпал или нет |

Поля `source:propose`:

| Поле | Тип | Смысл |
|---|---|---|
| `fingerprint.v` | `1` | версия схемы отпечатка (предложено, ждёт C) |
| `fingerprint.sizeBytes` | целое | размер файла в байтах |
| `fingerprint.sampleBytes` | целое | размер куска, 1 048 576 |
| `fingerprint.samples` | 3 строки | SHA-256 начала, середины и конца файла, hex |
| `durationMs` | целое или `null` | длительность, как её сообщил браузер; `null`, если браузер файл не открыл |
| `fileName` | строка | имя файла — только подсказка новичку, что смотрят |

Отпечаток не является полным хешем файла: браузерный API не умеет считать хеш
потоком, а читать весь многогигабайтный файл долго. Схема — из спайка C
(`decisions.md`, 6.1). Отпечатки совпадают, если совпадают все поля
`fingerprint`. Разные `v` не сравниваются: клиент сообщает «не удалось
сравнить», а не «другой файл». Длительность сравнивается отдельно,
с допуском около секунды, и нужна только для подсказки «похоже на тот же
фильм из другой раздачи». Поле `v` и длительность вне отпечатка —
предложение B: в прототипе C длительность входит в отпечаток, а версии
в JSON нет.

Отпечаток всегда снимается с исходного файла, даже если пользователь
нажал «Исправить звук»: исправленная копия другая по байтам
(`decisions.md`, 6.1). Сама проверка и исправление звука в протокол
не попадают — это дело клиента до входа в комнату. Выбранная звуковая
дорожка тоже не передаётся: на синхронизацию она не влияет.

### Воспроизведение

| Сообщение | Направление | Зачем |
|---|---|---|
| `playback:intent` | клиент → сервер | хочу играть, поставить паузу или перемотать |
| `playback:state` | сервер → всем | авторитетное состояние комнаты |
| `playback:hold` | сервер → всем | старт удерживается, вот кого ждём и до какого момента |

### Присутствие

| Сообщение | Направление | Зачем |
|---|---|---|
| `presence:update` | клиент → сервер | готовность плеера, запас буфера, состояние плеера, моё отклонение и когда оно измерено, ревизия, к которой я подготовился, моя задержка до сервера |
| `presence:sync` | сервер → всем | то же по всем участникам, плюс на связи ли участник |

Поля перечислены в `sync-start.md`, раздел 3.

Готовность не определяется одним признаком: браузер сообщает «данных достаточно»
при совсем небольшом буфере, и через секунду плеер снова встаёт. Поэтому
проверяется ещё и запас буфера.

**Готовность привязана к ревизии.** Клиент сообщает, к какой ревизии состояния
он уже подготовил плеер. Без этого барьер после перемотки отпустил бы старт
по старому «готов», присланному ещё до перемотки на новую позицию, — и игра
началась бы у всех, пока у кого-то буфер на новой позиции пуст.

**Задержка до сервера** нужна серверу, чтобы назначить якорь с запасом:
наибольшая задержка в комнате плюс 200 мс, но не меньше 300 мс.

**Отклонение** (`deviationMs`) нужно двоим. Интерфейсу — чтобы в списке
участников было видно, кто отстал. Голосу — чтобы задержать голос того,
кто смотрит впереди слушателя (`decisions.md`, 5.1). Поэтому у отклонения
строгие правила:

- **Знак:** плюс — участник отстаёт от комнаты, минус — опережает.
- **Момент замера** (`deviationAt`) — по серверным часам. Получатель
  приводит отклонения к одному моменту: у играющего участника отклонение
  почти не меняется со временем, а у того, кто стоит на подгрузке, растёт
  на столько, сколько прошло (если комната играет).
- **Нет отклонения** — `null`, когда сравнивать не с чем: нет файла или
  файл не совпал с комнатой. Ноль значит «идём вместе с комнатой»,
  а не «не знаю».
- Во время подготовки, подгрузки и перемотки отклонение честное, а не ноль
  и не `null`: плеер стоит, комната уходит вперёд, и именно тогда голосу
  нужна задержка. Что плеер стоит, видно по `playerState`.
- Насколько свежим должен быть замер, решает получатель по `deviationAt`.

Разрыв между слушателем и собеседником `j`:
`gapMs[j] = deviationMs(слушатель) − deviationMs[j]`, плюс — собеседник
впереди. В документе A та же разность записана через `driftMs` с обратным
знаком; здесь — в наших полях.

### Голос и текст: только пропуск в LiveKit

| Сообщение | Направление | Зачем |
|---|---|---|
| `media:token_request` | клиент → сервер | хочу подключить голос и чат; `requestId` |
| `media:token` | сервер → запросившему | `requestId`, адрес сервера LiveKit, токен, срок его действия, `roomSessionId`, мой `peerId` |

Сам голос, его сигналинг и текст чата идут напрямую между браузером
и сервером LiveKit, по нашему WebSocket — нет. Сервер выдаёт токен только
участнику комнаты; имя комнаты LiveKit и имя участника в ней (его `peerId`)
выбирает сервер, а не клиент. Поля, ошибки, жизненный цикл комнаты
LiveKit и переподключение — `voise-text-chats.md`, разделы 4–6.

Сообщений `chat:message` и `rtc:*` для голоса в протоколе больше нет.
Если дойдём до P2P-раздачи файла (не в MVP), её сигналинг добавится
отдельно: у LiveKit прямых соединений нет (`decisions.md`, 1.3).

## Три решения, определяющие архитектуру

### Позиция передаётся вместе с моментом, а не отдельно

Состояние воспроизведения несёт пару «позиция и момент по серверным часам,
которому она соответствует». Команды «играй сейчас» в протоколе нет вообще:
понятия «сейчас» в распределённой системе не существует, у каждого свои часы
и своя задержка. Клиент переводит момент в локальную шкалу сам.

Момент старта назначается с запасом вперёд, зависящим от наибольшей задержки
в комнате, — иначе самый медленный участник получит момент, уже прошедший
по его часам.

### У состояния есть номер ревизии

Клиент игнорирует состояние с номером меньше уже применённого. Без этого
двое, одновременно нажавшие паузу, могут привести третьего в неверное
состояние, если сообщения придут в обратном порядке.

Исключение — полный снимок `room:state` при входе и переподключении:
он применяется всегда, даже если номер не вырос.

В состоянии есть поле `setBy` — кто вызвал изменение. Оно нужно только
интерфейсу («Аня поставила паузу»).

### Барьер готовности холодный и с дедлайном

Сервер удерживает старт, пока не готовы все, — но только при первом запуске
и после явной перемотки. При входе нового участника и при подвисании
не удерживает.

Горячий барьер означал бы, что один слабый канал останавливает просмотр всем.
Дедлайн ограничивает ожидание: по его истечении комната стартует,
а отставшие догоняют сами.

## Что не является намерением

Когда клиент догоняет комнату после расхождения, он перематывается локально
и **не отправляет намерение**. Иначе сбой одного участника менял бы состояние
комнаты и размножался на всех.

Локальная коррекция скорости воспроизведения в протокол тоже не попадает:
это внутреннее дело клиента, комната о ней не знает.

**События элемента video не превращаются в намерения никогда.** `pause`,
`seeked`, `ratechange` возникают и от команд сервера, и от самого браузера
(Chrome ставит скрытое беззвучное видео на паузу). Если отправлять их
на сервер, возникает петля: пауза от сервера → событие → намерение →
сервер → … Так ломались Syncplay и Microsoft Live Share. Намерения
рождаются только из кнопок интерфейса.

## Ограничения

**Частота.** Намерения, пинги, запросы токена и отчёты о присутствии
ограничены по частоте. Превысивший получает ошибку `rate_limited`,
и интерфейс её показывает, а не молчит. Отдельно важна перемотка: перетаскивание ползунка
не должно порождать поток намерений, потому что каждое поднимает барьер
у всех. Намерение отправляется по завершению перетаскивания.

**Размер комнаты.** До четырёх участников (`room_full` для пятого);
один может сидеть и ждать остальных. Голос идёт через сервер LiveKit,
поэтому дело не в числе соединений: каждый клиент принимает и сводит
до трёх голосов. Нагрузку на клиента ещё не проверяли, и больше четырёх
без проверки не обещаем. Комнате LiveKit задаётся тот же предел.

**Ошибки.** Комната не найдена, комната заполнена (`room_full`), файл
не совпал, действие не разрешено, превышена частота (`rate_limited`).
На запрос токена — ещё три: участник не в комнате (`not_joined`), сессия
комнаты закрыта (`room_closed`), голос и чат недоступны
(`media_unavailable` — просмотр при этом продолжается).

## Внутри клиента

Главный поток и воркер синхронизации обмениваются сообщениями напрямую.
Это такой же контракт, хоть он и не уходит в сеть.

**Вниз, воркеру:** намерение пользователя; данные о показанном кадре;
выбранный источник с отпечатком; смена видимости вкладки; запрос токена
LiveKit.

**Вверх, главному потоку:** подготовить позицию; стартовать в такой-то момент;
поставить паузу; изменить скорость; запросить у пользователя файл; токен
LiveKit; обновить состояние для отрисовки, включая отклонения участников
для задержки голоса.

Позиция снимается не из обычного свойства плеера, а из данных о кадре:
обычное свойство является приближением и обновляется с непредсказуемой
частотой. Смена видимости важна потому, что в скрытой вкладке кадры
перестают приходить.

---

## Чего в протоколе нет

Передачи прав и роли хоста. Изгнания участников и паролей на комнату.
Сохранения состояния между перезапусками — комната живёт в памяти и исчезает,
когда из неё выходит последний. Истории чата: текст идёт через LiveKit
и на сервере не хранится. У каждого — лента последних сообщений в памяти
вкладки, опоздавший видит только новые.
