# Спайк: звук скачанных фильмов в браузере (MKV, AC-3, E-AC-3, DTS)

Код и замеры — `spikes/media-compat/`. Полный разбор рынка, причин и вариантов
со ссылками на источники — `media-compat-research.md` рядом.

## Вывод: берём «Исправить звук» в браузере

- **Проблема настоящая.** Типичный скачанный фильм — MKV со звуком Dolby (AC-3,
  E-AC-3) или DTS. Chrome и Firefox показывают такой фильм без звука и без ошибки,
  Safari не открывает MKV вообще. Проверено на 13 роликах в трёх браузерах.
  Производители браузеров это менять не собираются.
- **Ни один из найденных сервисов совместного просмотра это не решает,** не жертвуя
  чем-то важным: Syncplay требует установки, watchparty.me отправляет файл на сервер,
  остальные играют только то, что умеет браузер. (Код twoseven закрыт — что он делает
  внутри, мы не знаем.)
- **Решение для MVP:** проверка файла до входа в комнату и кнопка «Исправить звук».
  Прямо во вкладке видео копируется без изменений, выбранная звуковая дорожка
  перекодируется в кодек, который этот браузер точно играет, результат — MP4
  в хранилище браузера. Файл не покидает компьютер, движок синхронизации не меняется.
  MP4 с AAC Safari играет, поэтому ожидаем, что исправленный файл откроется и в нём;
  сам прототип в Safari ещё не запускали.
- **Прототип работает в Chromium.** На двух ядрах синтетический двухчасовой фильм
  с AC-3 (2,9 ГиБ) переделывается за 3,2 минуты, с DTS (3,8 ГиБ) — за 4,9 (звук в Opus,
  встроенный кодировщик). С AAC через wasm-кодировщик — худший случай, он понадобится
  Safari 18 — за 7,3 и 8,2 минуты. Время первого кадра в результате совпадает
  с исходником, поэтому ожидаем, что исправленный файл синхронизируется с друзьями.
- **Что осталось проверить:** прототип в настоящих Chrome, Firefox и Safari на настоящих
  фильмах в 4–8 ГБ, и что исправленный файл действительно идёт кадр в кадр с исходником
  (раздел 9). До этого все числа — с одной машины и синтетических файлов.

## 1. Что происходит

Подробные таблицы — `spikes/media-compat/results/browsers-2026-10-06.md`.

| Звук в файле | Chrome 154 (Windows) | Firefox 157 (Windows) | Safari 18.6 (Mac) |
|---|---|---|---|
| AAC в MKV | есть | есть | MKV не открывается |
| AC-3 / E-AC-3 / DTS в MKV | нет, ошибки нет | нет, ошибки нет | MKV не открывается |
| FLAC в MKV | есть | нет | MKV не открывается |
| AC-3 + AAC в MKV | есть: играет AAC | есть: играет AAC | MKV не открывается |
| AAC в MP4 | есть | есть | есть |
| AC-3 / E-AC-3 в MP4 | нет | нет | **есть** |
| FLAC в MP4 | есть | есть | **нет** |
| Opus в MP4 | есть | есть | есть |
| AC-3 + AAC в MP4 | **нет** | есть: играет AAC | есть |

Звук **во всех трёх браузерах** даёт только AAC в MP4 (и Opus в MP4, но Safari
на вопрос о нём отвечает «нет»).

Ещё две ловушки:

- **Выбор дорожки.** В MKV Chrome и Firefox играют первую дорожку, которую умеют.
  Русский дубляж в AC-3 рядом с оригиналом в AAC превратится в оригинал — молча.
  В MP4 Chrome играет только «включённую» дорожку, а ffmpeg включает лишь первую,
  поэтому MP4 «AC-3 + AAC» в Chrome молчит.
- **Переключить дорожку нельзя.** API `audioTracks` по умолчанию есть только в Safari.

## 2. Почему так

- **Chrome:** декодеры AC-3/E-AC-3 включаются флагами сборки только для Cast-устройств
  и tvOS, DTS выключен везде. Неподдерживаемую дорожку демультиплексор просто
  выбрасывает — отсюда «картинка есть, звука нет, ошибки нет».
- **Firefox** открывает MKV с версии 145 (ноябрь 2025) и сразу ограничил список
  кодеков: AVC, HEVC, VP8, VP9, AV1, AAC, Opus, Vorbis. Задач на AC-3/DTS нет;
  FLAC в MKV отложен как «<0.5 % использования».
- **Safari** декодирует Dolby средствами macOS (поэтому MP4 с AC-3 у него звучит),
  но Matroska не открывает.
- **Edge** на Windows может играть AC-3 через системный кодек, но с Windows 11 24H2
  этого кодека в чистой установке нет.

Патенты на AC-3 истекли в 2017 году, последний патент E-AC-3 — по всей видимости,
в январе 2026-го. Но планов добавить эти кодеки нет ни у одного браузера. Ждать нечего.

Источники — `media-compat-research.md`, разделы 1–2.

## 3. Насколько это часто

Статистики нет ни у кого. Качественно: релизы со стриминговых сервисов (WEB-DL)
обычно идут с E-AC-3, рипы Blu-ray — с DTS, DTS-HD MA и TrueHD, правила
релиз-групп с 2016 года требуют MKV, русский дубляж часто в AC-3/E-AC-3.
Жалобы «MKV без звука» на форумах Emby, Jellyfin, watchparty.me, Brave повторяются
с 2018 года. Для скачанного фильма MKV с Dolby или DTS — скорее правило.

## 4. Как решают другие

| Подход | Примеры | Своя копия | Любой кодек | Только браузер | Файл не уходит |
|---|---|---|---|---|---|
| Синхронизация настольных плееров | Syncplay | да | да | нет | да |
| Своя копия в браузере | twoseven, мелкие проекты | да | нет | да | да |
| Хост транслирует экран | Kosmi, Discord, watchparty.me | — | частично | да | нет |
| Перекодирование на сервере | watchparty.me Plus ($5/мес), Jellyfin, Plex, Emby | — | да | да | нет |
| Каталоги и ссылки | Watch2Gether, Rave, VK Звонки, Wink | нет | — | да | — |
| **Мы** | | да | да | да | да |

Ячейка «браузер + своя копия + любой кодек» пуста. Библиотеки, которые её закрывают,
появились только в 2026 году: wasm-декодеры AC-3/E-AC-3 для Mediabunny — в феврале,
DTS — в августе. Наша синхронизация к тому же на порядок точнее, чем у Syncplay
(у него перемотка при расхождении больше 1 с).

## 5. Варианты решения

| Путь | Что даёт | Цена | Решение |
|---|---|---|---|
| Проверка файла до входа + совет с командой ffmpeg | понятный диагноз вместо тишины | пользователь чинит сам | **сейчас** |
| **Конвертация звука в браузере** (Mediabunny → MP4) | звук AC-3/E-AC-3/DTS везде, MKV в Safari (ожидаем, не проверено), движок не меняется | ожидание, копия файла, нет TrueHD | **сейчас, основной путь** |
| Electron + встроенный ffmpeg | всё, включая TrueHD | установщики, подпись приложений | запасной план |
| Звук отдельно от картинки (wasm + WebAudio) | без ожидания и копии | синхронизация звука с картинкой, нет Safari | после курса |
| MKV → фрагментированный MP4 → MSE на лету | без ожидания, `<video>` сохраняется | перемотка и буферы — своя забота | после курса |
| Готовый wasm-плеер (libmedia и др.) | всё | вывод в canvas, переписать синхронизацию | нет |
| Хост транслирует фильм | — | звук Dolby не передаётся тоже, фильм уходит с компьютера | нет |
| Локальный помощник на localhost, расширение | нативный ffmpeg | запросы разрешений, Safari не пускает, установщики | нет |

Почему не ffmpeg.wasm: предел памяти 2 ГБ (многопоточная сборка — 1 ГБ), результат
держится в памяти, сборка на FFmpeg 5.1 под GPL. Фильм на 4–8 ГБ туда не влезает.

Почему Electron не лечит сам по себе: в его Chromium тех же декодеров нет.

## 6. Прототип

`spikes/media-compat/` — страница «Исправить звук» и автоматический замер.

**Что делает:**

1. Читает заголовок файла (Mediabunny): контейнер, видео, звуковые дорожки с языком,
   каналами и флагом «основная».
2. Даёт прогноз для текущего браузера по правилам из замеров (`src/verdict.ts`), затем
   проверяет на деле: открывается ли файл и есть ли звук при коротком беззвучном
   проигрывании. Где браузер сообщает о звуке, главнее проверка: Chrome — счётчиком
   декодированных байт, Firefox — флагом `mozHasAudio` (это флаг, а не счётчик, но на
   13 роликах он совпал со слышимым). Если проигрывание не началось (например, вкладка
   в фоне), страница пишет «не удалось проверить» и остаётся при прогнозе.
3. По кнопке перекладывает файл в MP4: видео копируется, выбранная дорожка — копируется,
   если она уже в нужном кодеке, иначе перекодируется в AAC (или Opus по выбору).
   Остальные дорожки отбрасываются, поэтому вопрос «какую дорожку выберет браузер»
   исчезает. Дорожки, которые нельзя ни скопировать, ни декодировать (TrueHD), в таблице
   помечены «нельзя исправить», по умолчанию выбирается первая исправимая. Если выбрать
   такую дорожку, страница остановится с объяснением, а не сделает немой файл
   (проверено на синтетическом ролике с TrueHD). Если скорость падает ниже 2× реального
   времени — признак того, что видео перекодируется, — страница предупреждает.

   В продукте кодек стоит выбирать по браузеру, ведь исправленный файл нужен только
   тому, кто его исправил: Chrome и Edge — AAC (встроенный кодировщик), Firefox —
   Opus (встроенный кодировщик; MP4 с Opus в Firefox звучал), Safari — копия Dolby для
   AC-3 и E-AC-3, AAC для DTS.
4. Пишет результат в приватное хранилище браузера (OPFS) через воркер. По MDN это
   единственный способ записи в файл, который есть во всех трёх браузерах, включая
   Safari 18; в Firefox и Safari сам прототип не запускали. Гигабайты не держатся
   в памяти. При отмене или ошибке недописанный файл удаляется (проверено в Chromium:
   после отмены хранилище пустое, повторная конвертация проходит).
5. Проверяет результат: открывается ли, есть ли звук, совпадает ли время первого кадра
   с исходником. Даёт сохранить копию на диск.

**Замер в Chromium 141** (Playwright, Linux, 2 ядра Xeon 2,1 ГГц), файлы
`tools/make-big-sample.sh`: 2 часа, H.264 720p 3 Мбит/с, звук 5.1, видео копируется,
звук сводится в стерео. Сырые результаты — `results/bench-2026-10-06-*.json`.

| Файл | Звук в результате | Время | Скорость | Шкала времени |
|---|---|---|---|---|
| 2 ч, AC-3 5.1, 2,9 ГиБ | Opus (встроенный кодировщик) | 3 мин 14 с | 37× реального | первый кадр 0,005 → 0,005 с |
| 2 ч, DTS 5.1, 3,8 ГиБ | Opus (встроенный кодировщик) | 4 мин 53 с | 25× | 0 → 0 |
| 2 ч, AC-3 5.1, 2,9 ГиБ | AAC (wasm-кодировщик) | 7 мин 20 с | 16× | 0,005 → 0,005 с |
| 2 ч, DTS 5.1, 3,8 ГиБ | AAC (wasm-кодировщик) | 8 мин 10 с | 15× | 0 → 0 |

Пиковая память всех процессов Chromium во время конвертации с AAC — около 1,4 ГБ при
файлах на 2,9–3,8 ГиБ: фильм целиком в память не загружается. Как мерили —
`tools/rss.py`, результат — `results/memory-2026-10-06.txt`.

Короткие ролики VP9 с AC-3, E-AC-3, DTS и «AC-3 + AAC» после конвертации в Opus играют
со звуком (браузер сообщил, что звук декодирован). Результат в AAC в этом Chromium
не проверить: в нём нет декодера AAC. Длительность результата отличается от исходника
на 0,02–0,03 с.

**Что это показывает:** на двух слабых ядрах синтетический двухчасовой фильм
(720p, 3 Мбит/с) укладывается в критерий отчёта «не дольше 10 минут», даже
с wasm-кодировщиком AAC. Настоящие фильмы в 4–8 ГБ, Firefox и Safari не проверены —
это раздел 9. Движок синхронизации менять не нужно: он работает с любым `<video>`.

**Чего прототип ещё не доказал:**

- В Chromium из Playwright нет AAC и H.264, поэтому проигрывание AAC-результата здесь
  не проверить. Нужен настоящий Chrome.
- Firefox и Safari не запускались. В Safari 18 нет WebCodecs для звука вообще —
  там и декодер, и кодировщик будут wasm; это самый медленный путь.
- Квоты хранилища на гигабайтных файлах в Firefox и Safari не проверены. Ограничения
  по документации и правила очистки — в разделе 8, «Хранилище и очистка».
- TrueHD Mediabunny не умеет. Прототип помечает такую дорожку «нельзя исправить»
  и по умолчанию выбирает другую — в BD-рипах рядом обычно лежит AC-3 на том же языке.
  Если исправимой дорожки нет, остаётся совет с командой ffmpeg.
- DTS-HD MA: декодируется ли что-то кроме ядра DTS — не проверено.

## 7. Проверка файла до входа в комнату

Правила прогноза — `src/verdict.ts`, без DOM и без библиотек:

- контейнер и кодек спрашиваются у браузера с **настоящим** MIME файла
  (`video/x-matroska; codecs="ac-3"`), а не подставляя MP4;
- Safari и MKV — «не откроется» независимо от ответа;
- поправки там, где Safari отвечает неверно: FLAC в MP4 — без звука, Opus в MP4 — со звуком;
- выбор дорожки: в MP4 у Chrome, Edge и Safari — только «включённая»; в остальных
  случаях — первая, которую браузер умеет.

41 тест (`npm test`): 39 из них прогоняют все 13 роликов × 3 браузера с ответами
canPlayType из отчётов и сравнивают с тем, что было услышано на самом деле; ещё два
проверяют определение браузера по User-Agent и выбор плана конвертации.

Прогноз — только первый фильтр. Устаревший Chrome (в Playwright — 141) на любой MKV
отвечает «не смогу», хотя играет его. Поэтому после прогноза страница открывает файл
и коротко проигрывает его без звука: Chrome и Firefox сообщают о звуке (см. раздел 6).
В Safari такой проверки нет — остаётся прогноз.

## 8. Что это меняет в архитектуре

- **Новый модуль клиента «подготовка файла»** до входа в комнату: проверка, кнопка
  и хранилище исправленных копий с очисткой (ниже). Mediabunny с wasm-расширениями —
  около 5 МБ JavaScript; загружать их только когда кнопка нужна.
- **Отпечаток файла** (`decisions.md`, 6.1) снимается с исходного файла, до конвертации.
  Исправленный файл другой по байтам; чтобы приложение узнало его в следующий раз,
  отпечаток исходника стоит записать в метаданные результата — это не сделано.
- **Движок синхронизации не меняется.** Время первого кадра результата совпадает
  с исходником (по чтению файла Mediabunny). Что браузеры показывают тот же кадр при том
  же `currentTime`, ещё надо проверить (раздел 9).
- **Safari**, скорее всего, перестаёт быть отдельной проблемой: MP4 с AAC он играет
  по замерам на роликах, значит, должен сыграть и исправленный файл. Сам прототип
  в Safari не запускали.
- **Документы поправлены:** `decisions.md` 6.3 и 6.5, модули, риски и технологии
  в `architecture.md`, поля `source:propose` в `protocol.md` (отпечаток исходника;
  выбранную дорожку не передаём — на синхронизацию она не влияет), шаг проверки
  файла в `sync-latejoin.md`.

### Хранилище и очистка

Исправленный файл — полная копия фильма, 2–8 ГБ, в хранилище браузера (OPFS) на диске
пользователя. Пользователь эту папку не видит и сам удалить копию не может — разве что
через «Очистить данные сайта». Значит, убирать за собой должно приложение, иначе
у человека тихо копятся гигабайты.

**Сколько разрешено занять** (по MDN, у нас не проверено):

| Браузер | Сколько можно сайту | Когда браузер удалит сам |
|---|---|---|
| Chrome, Edge | до 60 % диска | при нехватке места на диске |
| Firefox | меньшее из 10 % диска и 10 ГиБ; с разрешения `persist()` — до 50 % | при нехватке места на диске |
| Safari (macOS 14+) | около 60 % диска | при нехватке места; и если на сайт не заходили 7 дней |

Удаляет браузер сразу всё хранилище сайта, начиная с давно не открытых сайтов.
После `navigator.storage.persist()` данные удаляет только сам пользователь. В Firefox
этот вызов показывает пользователю запрос, в Chrome и Safari ответ даётся без запроса.
Одно хранилище на весь сайт: исправленные копии делят квоту со всеми остальными
данными приложения.

**Правила для продукта:**

1. **Своё — в одной папке.** Все копии лежат в папке хранилища, например `fixed/`.
   Рядом — список: отпечаток исходника, имя, размер, когда создана, когда последний раз
   открыта. Удаляем только по этому списку и никогда не очищаем всё хранилище сайта.
2. **Перед конвертацией предупреждаем и проверяем место.** Говорим, что появится
   копия фильма примерно такого-то размера. `navigator.storage.estimate()` против
   размера фильма с запасом. Не хватает — не начинаем и показываем, какие копии можно
   удалить. В Firefox, если фильм не помещается в 10 ГиБ, объясняем и просим
   `persist()`. Без нужды `persist()` не просим: с ним браузер не уберёт забытое за нас,
   и очистка целиком на приложении.
3. **Отмена или ошибка** — недописанный файл удаляется сразу.
4. **Одна копия за раз.** Исправили новый фильм — предыдущая копия удаляется,
   пользователь видит об этом сообщение.
5. **Выход из комнаты:** «Исправленная копия занимает 2,6 ГБ. Удалить сейчас или
   оставить на 7 дней?»
6. **При каждом запуске** удаляем копии, которые не открывали 7 дней.
7. **«Сохранить копию» в обычную папку** — после сохранения копия в хранилище
   удаляется. Дальше пользователь выбирает сохранённый файл, как любой другой.
8. **Экран «Хранилище» в настройках:** список копий с размером, «Удалить»
   и «Удалить исправленный звук» (все наши копии).
